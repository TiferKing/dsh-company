# 员工总数与执行并发取消固定上限的可行性评估

日期：2026-09-06。第 1–7 节保留改造前 `dsh-company@0.16.1` 的设计论证与基线证据，章节中的“当前”指该基线；旧行号也属于评估时源码。用户同意建议后，工作区已实现 `0.17.0`，现行运行说明以[架构文档](architecture.md)为准，没有改动实际公司数据或安装 profile。

## 实施进展：0.17.0

- 编制支持 `unlimited`，新公司默认不设上限；有限整数继续有效，旧公司通过人类批准的治理请求显式扩容。
- 员工、组织、岗位实施服务端分页，汇总覆盖全公司；每轮调度/治理通知批量独立为 64。
- 共享执行准入覆盖工作、HR、邮件、欢迎和恢复，提供 adaptive/fixed/unlimited；Host 已接受但尚未运行的输入也占名额。取消任务清理等待诊断，旧 runtime 卸载后不能重新开放准入。
- usage 与完整审计改为独立历史追加；WAL v2、旧格式读取、不可变热视图和写入压力统计已接入。**实体增量存储、持久用量索引与流式水合尚未完成**：完整事务仍随人数和历史长度增长，超过缓存预算时会重新读取历史。
- 回归覆盖第 33 名实际招聘、超原边界的员工历史校验、1,001 名员工分页、同岗位超 64 人、跨公司执行、资源等待恢复、历史重放与写失败。它们是合成状态及模拟 Host 测试，不是 1,001 名真实模型员工并行运行压测。

因此可以使用“不设固定业务人数上限”和“资源自适应执行”，不能据此宣称无限资源容量或已经根治长时间运行 OOM。

## 1. 结论与“无上限”的含义

**可以把员工人数做成不设固定业务上限，也可以不配置固定的同时执行人数；但现有实现不能仅删除 `32` 就提供可长期运行的无限规模公司。**

| 目标 | 判断 |
| --- | --- |
| 不因达到 32、64、256 等预设人数而拒绝招聘 | 可实现；需要同步修改存档、接口与界面契约，并让数据按需读取 |
| 不配置固定执行并发数，由资源和服务状态决定实际执行规模 | 可实现，但需要新增资源准入、排队与恢复机制 |
| 所有获批员工一有任务就立即运行，连资源压力下的排队也取消 | 代码可以放行；无法论证其在有限硬件和外部服务条件下长期稳定，不建议作为默认运行模式 |

“自适应执行”仍会动态限制新任务启动，只是没有一个固定的并发人数常量。它不能被描述为完全没有并发控制。预算、人工批准、每员工单轮执行和任务依赖等业务约束也不因人数放开而失效。

## 2. 当前到底限制了什么

| 层次 | 当前限制 | 证据与含义 |
| --- | --- | --- |
| 插件配置 | 默认 8 名，允许 1–32 名 | [index.ts](../src/index.ts:28)、[schemas.ts](../src/schemas.ts:25) |
| 招聘准入 | 非退休员工数达到 `min(公司保存上限, 当前配置上限)` 时拒绝 | [runtime.ts](../src/runtime.ts:614)；HR 占名额，暂停和失败仍占名额 |
| 已有公司 | 创建时把上限写入公司存档，读取时再校验 | [runtime.ts](../src/runtime.ts:242)、[schemas.ts](../src/schemas.ts:205)；调高配置不会自动扩容旧公司 |
| 员工历史 | 在职与退休记录累计最多 10,000 条 | [schemas.ts](../src/schemas.ts:206)；不是单纯的在职名额限制 |
| 员工执行 | 没有独立的全局员工并发池 | [scheduler.ts](../src/scheduler.ts:186)；逐个投递后，各会话可以继续并行执行 |
| 普通工作 | `maxOpenWorkItems` 默认 32，配置最高 1,000 | [index.ts](../src/index.ts:31)、[work.ts](../src/work.ts:56)；计数是 `claimed/in_progress`，不能当成覆盖 HR、邮件、欢迎轮次的统一执行并发限制 |
| 扩编流程 | 活跃招聘请求受待审批数量上限约束 | [runtime.ts](../src/runtime.ts:431)；限制待处理积压，不限制累计可招聘人数 |

取消员工总数限制，需要同时处理配置解析、存档读取校验、招聘比较及相关数组校验。普通工作准入上限是否继续保留，应单独明确；保留它时，不能声称普通工作也已完全放开。

## 3. 移除 32 后还会碰到的界面边界

| 边界 | 当前值 | 代码 |
| --- | --- | --- |
| 整份快照中的员工记录 | 256 | [client/types.ts](../src/client/types.ts:1102) |
| 同一岗位关联的员工 | 64 | [client/types.ts](../src/client/types.ts:663) |
| 快照中的组织单元 | 256 | [client/types.ts](../src/client/types.ts:1108) |
| 快照中的岗位 | 1,000 | [client/types.ts](../src/client/types.ts:1112) |
| 单组织直接子节点 | 128 | [client/types.ts](../src/client/types.ts:650) |
| 单组织关联岗位 | 256 | [client/types.ts](../src/client/types.ts:651) |
| 客户端接受的 HTTP 响应 | 16 MiB | [client/store.ts](../src/client/store.ts:10) |

Host 快照保留全部在职员工，通常还保留最近 200 条退休员工记录，[snapshot.ts](../src/snapshot.ts:61)。因此，例如 57 名在职员工加 200 条退休记录，就会超过客户端的 256 条限制。前端收到的是整份快照，超过任意数组契约都可能导致整个快照解析失败。

本轮使用测试快照、唯一员工 ID 和真实 `parseCompanySnapshot`，在独立进程中进行了以下实验，没有创建真实员工或调用模型：

| 合成输入 | 结果 |
| --- | --- |
| 256 名员工，岗位只引用 1 名 | 通过 |
| 257 名员工，岗位只引用 1 名 | 拒绝：`snapshot.employees must be an array with at most 256 entries` |
| 64 名员工，同一岗位引用全部 64 名 | 通过 |
| 65 名员工，同一岗位引用全部 65 名 | 拒绝：`snapshot.positions[0].employee_ids must be an array with at most 64 entries` |

这些实验证明隐藏契约确实会阻止扩容，不是推测；它们不是吞吐或内存压测，不能证明 256 名真实员工可以稳定执行。

## 4. 宿主允许编制与活跃会话分离

本节宿主路径均相对于 `/home/tiferking/.nvm/versions/node/v26.7.0/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/`。检查当前安装的 `dsh-subagent/lib/index.js`：

- `1124–1135`：会话非运行中、没有等待接收的输入且没有占用的子会话时，满足 settled 条件。
- `1377–1408`：`watchSettlement` 触发清理。
- `1432–1465`：等待持久化后调用 handle dispose、删除 activation 并释放 ownership。

公司通过固定 session ID 创建 continuable 会话，再通过同一 ID 跟进，[employees.ts](../src/employees.ts:209)。因此，员工身份可以长期保留，满足条件的执行会话则可冷卸载；扩大编制不等于必须让全部员工会话永久常驻 RAM。存在未完成输入或子会话时不会立即满足卸载条件，恢复长历史也仍有开销。

本轮在所检查的宿主服务路径中没有发现全局固定员工总数或同时运行 Agent 数量的上限。每个 Agent 的单 driver 执行与 `maxDepth` 委派深度是不同约束，不能当作直接员工人数限制。公司显式传入自己的 `memberMaxDepth`；通用 subagent 模型工具的默认深度不代表公司服务调用另有同样的宽度限制。

还有几种独立约束：`dsh-agent-loop/lib/index.js:230` 的每 Agent 工具并行默认值为 10，并保留独占工具执行边界；`dsh-subagent/lib/index.js:1697`、`:1815` 的冷会话扫描并发为 4。它们分别约束单员工工具执行和一次本地扫描，不是整个公司的员工并发上限。显式 child ID 创建还会列举快照检查重复，`:804–810`，人员增长会增加该路径的扫描成本。

模型服务也可能要求退避：`dsh-llm-deepseek/lib/index.js:1317` 与 `dsh-llm-pi-ai/lib/index.js:1268` 将 HTTP 429 映射为 `RATE_LIMIT`，`dsh-llm-retry/lib/index.js:131–150` 按策略处理重试及有效的 Retry-After。本地代码无法确定账户实际请求或 Token 配额；放开公司并发不会取消服务端限制，也不应预设所有服务都是同一额度。

## 5. 当前阻碍稳定扩容的是全量操作与积压

### 5.1 公司存储不是按员工或事件局部更新

每个公司事务都会读取、解析并校验完整状态，克隆状态写入 WAL，再重写完整 `company.json`，[state.ts](../src/state.ts:344)。状态包含累计用量明细，文件大小会随运行历史增长。

调度器遍历员工时重复调用 `readActive`，[scheduler.ts](../src/scheduler.ts:186)。若人数为 N、完整状态大小为 S，一轮扫描仅重复读取和解析部分就涉及约 N×S 的处理量，校验、任务选择和其他读取还会增加开销。这是累计处理量，不等于同一时刻的内存占用。

### 5.2 当前分页没有减少后台全量处理

HTTP 状态接口生成完整快照后计算 ETag；304 也不能省掉前面的完整读取与投影。工具的分页则发生在 `runtime.status` 已生成快照之后，[tools.ts](../src/tools.ts:393)。

快照对每个员工扫描用量账本，部门负载又按员工扫描工作项，[snapshot.ts](../src/snapshot.ts:81)、[snapshot.ts](../src/snapshot.ts:474)。人数和用量历史同时增长时，计算量会相乘。前端折叠组织树也不等于后端分页或虚拟列表。

### 5.3 合并调度唤醒没有限制所有写入积压

现有 scheduler pump 合并重复唤醒，解决的是重复调度任务。公司事务仍按 Promise 链排队，[state.ts](../src/state.ts:659)；记账也为真实用量事件逐个排队，[accounting.ts](../src/accounting.ts:52)。这些事件不能当作可丢弃的旧界面刷新。

如果持续产生的状态写入速度超过存储处理速度，等待数量就会增长。可表示为：一段时间内新增积压约等于 `max(0, 写入到达速率 − 处理速率) × 时间`。释放员工人数限制并允许更多会话同时产生事件，会增加这种压力；仅合并 scheduler kick 不能保证记账与持久化队列有界。

金额预算也不能替代资源控制：零价模型可以不消耗金额预留，但仍消耗会话、CPU、内存与 I/O；收费模型的预算约束也没有表达本机能够同时处理多少事件。

之前记录的 OOM 表明该部署存在真实的内存压力问题，[排查记录](dsh-oom-diagnosis.md)。已修复的历史记账并发放大和调度队列问题，不构成任意人数、任意运行时长下稳定性的证明。本轮没有对真实公司进行大规模执行压测，也没有取得退出进程的堆快照。

## 6. 建议的实现顺序

1. **定义配置语义与旧公司迁移。** 人数支持明确的“不设业务上限”模式；有限整数继续有效。当前配置、公司快照与升级路径使用同一规则，旧公司保留已有值，用户可以显式扩容。使用可持久化的明确标记，不用 `Infinity` 或任意超大整数假装无上限。
2. **将批处理大小与人数解耦。** 治理通知每轮处理量现在直接使用 `config.maxEmployees`，[scheduler.ts](../src/scheduler.ts:252)。即便人数不封顶，每批执行仍应有限、可让出执行权，并从持久游标继续。
3. **先打通查询链路。** 员工、岗位成员和历史记录采用服务端分页；列表契约限制每页大小，响应体保护继续保留。前端按需加载，汇总使用独立统计，账本归属和审计引用在历史分离后仍可追溯。
4. **把高频状态和账本改为局部处理。** 建立员工、任务、用量归属索引和累计汇总；按事件或实体持久化，避免每条状态事件都重写公司全部历史。完整校验保留在恢复或检查点等适当边界。
5. **统一执行准入。** 覆盖工作、HR 评估、邮件、欢迎轮次及恢复投递，不能只限制普通工作。可以提供固定并发、自适应执行以及显式实验性的无固定并发模式。自适应模式根据内存余量、事件循环延迟、持久化积压和服务退避决定是否启动下一轮。
6. **保持按需激活与可恢复排队。** 复用宿主已提供的 continuable 清理机制，避免批量恢复所有空闲员工；资源不足时保留排队原因与任务标识，资源恢复后继续派发。不同公司共享宿主时，还需要共同考虑宿主资源，不能只看单家公司。

本建议没有把自适应排队称为“完全没有并发限制”。如果产品明确要求连这些保护也关闭，应把它作为可选择的执行策略，并明确其容量由宿主、机器与服务决定。

## 7. 何时可以宣称改造有效

应分别验证大编制少量活跃、大量短任务、少量长历史会话、多个公司同时执行与批量冷恢复，而不是只测试能否创建第 33 名员工。验证至少包括：

- 旧公司从有限人数调整后可以继续招聘，重启不会还原或误解释配置。
- 超过原来的岗位、员工和退休历史快照边界后，分页与组织统计仍完整可读。
- 同一员工不会重复获得执行轮次，HR、邮件和恢复入口遵守所选择的执行策略。
- 暂停与卸载能停止新准入，未完成工作、用量和预留在重载后正确恢复。
- 持续负载下观察 heap、RSS、事件循环延迟、持久化等待数量与等待时间；资源不足时系统保持可操作，并按策略排队或报告原因。
- 用量最终与持久账本一致，积压控制不丢失真实消费记录。

当前证据支持“可以重构为无固定业务人数，并提供无固定数值的执行策略”；不支持“现有版本删除若干常量即可安全地无限扩员、无限并行”。
